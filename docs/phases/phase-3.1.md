# Phase 3.1 — Multi-Tenancy Schema

**Tag:** `phase-3.1-complete`
**Commit:** *(this phase's commit — see `git log docs/phases/phase-3.1.md`)*

## What This Phase Accomplished

Phase 3.1 introduces the tenant boundary that every Role and UserRole
docstring since Phase 2.1 has been pointing at: two new tables
(`organizations`, `organization_memberships`) and a nullable
`organization_id` column added to both `roles` and `user_roles`. Schema
only — no repository, service, or API changes yet, mirroring how Phase 2.1
shipped RBAC's schema a full two sub-phases ahead of its service layer.

## Why It Was Needed

`Role` and `UserRole` were built global-only in Phase 2, with an explicit,
documented plan to add organization scoping "then" (Phase 3). Building the
schema as its own reviewable step — before any service logic depends on it
— let the trickiest part (preserving Phase 2.2's duplicate-assignment
guarantee once a nullable scoping column exists) get solved and tested in
isolation, the same discipline Phase 2.1 applied to the original RBAC schema.

## Files Created

- `app/domain/models/organization.py` — `Organization`: id, unique `name`,
  `created_at`. Deliberately minimal — a tenant is just an identity other
  tables reference.
- `app/domain/models/organization_membership.py` — `OrganizationMembership`:
  `(user_id, organization_id)` with `UniqueConstraint`, `joined_at`.
  Answers "is this user part of this org," a deliberately different
  question from "what role do they hold" (`UserRole`).
- `app/db/migrations/versions/714a446f6f38_add_organizations_and_organization_.py`
  — the schema migration (autogenerated, reviewed and hand-fixed — see
  below).
- `tests/integration/test_organization_models.py` — 16 tests against real
  Postgres.
- `docs/phases/phase-3.1.md` — this document.

## Files Modified

- `app/domain/models/role.py` — added `organization_id` (nullable, FK to
  `organizations.id`, `ON DELETE CASCADE`). `NULL` = global/system role
  (the four seeded roles stay `NULL` and remain usable everywhere);
  non-`NULL` = a custom role scoped to, and only assignable within, that
  one organization.
- `app/domain/models/user_role.py` — added `organization_id` (nullable,
  same FK/cascade shape). `NULL` = a global assignment — exactly Phase
  2/2.1's only possible meaning, so every pre-Phase-3 row is already
  correct without any backfill. Non-`NULL` = the assignment only grants
  the role's permissions within that organization. Replaced the single
  `UNIQUE(user_id, role_id)` constraint with two **partial** unique
  indexes (see Decisions below).
- `app/domain/models/__init__.py`, `app/db/migrations/env.py` — registered
  the two new models so `Base.metadata`/Alembic autogenerate see them.
- `tests/integration/test_fresh_database_migration.py` — strengthened to
  assert `organizations`/`organization_memberships` exist and that a fresh
  install seeds zero organizations with all four default roles global,
  matching the precedent Phase 2.1 set for this same test file.

## Tests Added

16 integration tests in `test_organization_models.py`: `Organization`
creation and unique-name enforcement; `OrganizationMembership` creation,
duplicate rejection, and cascade-delete from both the user side and the
organization side; `Role.organization_id` defaulting to `NULL`, being
settable to a real organization, and cascading (or explicitly *not*
cascading, for global roles) when that organization is deleted; and six
tests on `UserRole.organization_id` locking in the exact partial-index
behavior this migration exists for — duplicate *global* assignment still
rejected, the same role assignable to the same user in two different
organizations, duplicate assignment *within* one organization rejected,
a global and an org-scoped assignment of the same role coexisting as two
rows, and deleting an organization removing only its own scoped
assignments.

`test_fresh_database_migration.py`'s new assertions were also verified
directly against a genuinely fresh throwaway database created for this
purpose (the test itself can't run in this environment — see the
Verification note below — so its logic was exercised manually instead of
left unverified).

Full suite after this phase: **223 tests collected, 222 passing** (207
from Phase 1–2.4 + 16 new). The count intentionally excludes any change to
the one pre-existing environment-only failure carried since Phase 2.3
(`test_fresh_database_migration.py`'s main assertion, which needs a second
Postgres instance on port 5432 not available in this environment) — see
Verification below.

## Important Architectural / Security Decisions

- **No data backfill.** `organization_id` is added as nullable and left
  untouched on every existing row. This works because `NULL` already
  means exactly what every pre-Phase-3 role and assignment already was —
  global. `AuthorizationService`'s existing (not-yet-org-aware) callers
  will need zero changes in Phase 3.2/3.3 to keep working exactly as
  before: passing no `organization_id` resolves precisely the rows it
  always did.
- **Partial unique indexes, not one composite `UNIQUE` constraint, on
  `user_roles`.** PostgreSQL treats every `NULL` as distinct from every
  other `NULL` in an ordinary unique constraint. A plain
  `UNIQUE(user_id, role_id, organization_id)` would have silently stopped
  rejecting duplicate *global* assignments the moment this column existed
  — a real regression of a guarantee Phase 2.2 already shipped and tested
  (`test_duplicate_assignment_is_rejected`). Two partial indexes restore
  the original guarantee for the `NULL` case while adding the new
  per-organization one:
  `uq_user_roles_user_role_global` (`WHERE organization_id IS NULL`) and
  `uq_user_roles_user_role_org` (`WHERE organization_id IS NOT NULL`).
  This is directly why `test_duplicate_global_assignment_still_rejected`
  exists as its own explicit regression test, not just an inferred side
  effect of another test.
- **`roles.name` stays globally unique — not scoped per organization.**
  Two different organizations cannot both name a custom role "Support",
  and a custom role cannot reuse one of the four system role names. This
  is a deliberate, documented simplification over adding a second set of
  partial unique indexes for name uniqueness — it costs a small amount of
  admin-facing UX flexibility, not any security or correctness property
  (permissions are resolved by ID and by `(resource, action)`, never by
  role name), and can be revisited later if it becomes an actual pain
  point rather than a hypothetical one.
- **`UserRole` still references `users.id` directly, not
  `organization_memberships.id`.** An earlier docstring (Phase 2.1) framed
  this as a "known, planned migration for Phase 3." This phase deliberately
  did *not* make that change: coupling a role assignment to a specific
  membership row would mean losing that assignment the instant membership
  lapsed, which conflates two independently useful questions —
  "does this person belong to this org" and "what can they do, and where."
  Keeping them as separate tables, both keyed on `user_id`, preserves that
  distinction and was one of the explicit design options presented and
  approved before this phase began.
- **Both new foreign keys were given explicit constraint names.**
  Alembic's autogenerated migration created them unnamed
  (`create_foreign_key(None, ...)`), which leaves `downgrade()`'s matching
  `drop_constraint(None, ...)` with no stable name to target — a
  downgrade that would have failed at runtime the first time anyone ran
  it. Both were renamed to `roles_organization_id_fkey` and
  `user_roles_organization_id_fkey` (PostgreSQL's own default naming
  convention for an unnamed `ALTER TABLE ... ADD FOREIGN KEY`) before
  this migration was applied.

## Verification

- `alembic upgrade head` applied cleanly against the existing test
  database; `alembic check` reports zero drift between the models and the
  resulting schema (including both partial indexes).
- `alembic downgrade -1` → `alembic upgrade head` round-tripped cleanly,
  confirming `downgrade()`'s hand-fixed constraint names are correct in
  practice, not just in theory.
- `test_fresh_database_migration.py`'s existing assertion still cannot run
  in this environment — it requires a second, standalone Postgres
  reachable on port 5432 to `CREATE DATABASE` against, which isn't running
  locally (only the port-5433 test-db container is available). This is
  the same pre-existing, unrelated-to-this-phase limitation noted since
  Phase 2.3. Rather than leave this phase's new assertions unverified, a
  throwaway database was created directly against the available
  port-5433 instance, the full migration chain was run against it via
  `alembic upgrade head`, and every new assertion
  (`organizations`/`organization_memberships` tables exist, zero seeded
  organizations, all four default roles global) was confirmed true before
  the throwaway database was dropped.
- Full suite: 222/223 passing, zero regressions in any Phase 1–2.4 test.

## What This Phase Enables for Phase 3.2

A migrated, tested schema that Phase 3.2's repository layer
(`OrganizationRepository`, `OrganizationMembershipRepository`, and the
org-aware extensions to `RoleRepository`/`UserRoleRepository`) can build on
directly — no further schema changes anticipated for either Phase 3.2 or
Phase 3.3's `AuthorizationService` updates.
