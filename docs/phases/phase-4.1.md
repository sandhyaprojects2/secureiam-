# Phase 4.1 — Audit Log Schema

**Tag:** `phase-4.1-complete`
**Commit:** *(this phase's commit — see `git log docs/phases/phase-4.1.md`)*

## What This Phase Accomplished

Phase 4.1 introduces `audit_logs`: a single, append-only table for
recording security-relevant events — who did what, when, and to what.
Schema only, mirroring the precedent set by every earlier multi-part
phase (2.1, 3.1): the trickiest design questions (nullability, delete
behavior, extensibility) get solved and tested in isolation before any
service is wired to write to it.

## Why It Was Needed

Every prior phase's own documentation flagged this gap explicitly:
`UserRepository.update_last_login()`'s docstring calls itself
"audit-adjacent metadata only... not the audit log itself (that's Phase 4)",
and both Phase 2.3 and 2.4's docs list "audit logging (Phase 4)" as a named
follow-on. An IAM system with role/permission management but no record of
who changed what — or who tried and failed to log in — has a real gap for
security monitoring and compliance, which is exactly what this phase closes.

## Tests Added

6 integration tests: creation with minimal fields (everything nullable
actually null), creation with every field populated, JSONB metadata
round-tripping a nested structure, and the two guarantees this table
exists for — deleting the actor user or the referenced organization sets
the corresponding foreign key to `NULL` on the audit row rather than
deleting it (unlike every `CASCADE` relationship elsewhere in this
schema) — plus a sanity check that multiple rows for the same actor are
all retained (no accidental uniqueness constraint).

Full suite after this phase: **302 tests collected, 301 passing** (296
from Phase 1–3.4 + 6 new). The one non-passing test is the same
pre-existing environment limitation carried since Phase 2.3; its new
`audit_logs`-related assertions were independently verified against a
throwaway database, the same way every prior phase's fresh-install
assertions were.

## Important Architectural / Security Decisions

- **`ON DELETE SET NULL`, not `CASCADE`, on both `actor_user_id` and
  `organization_id`.** Every other foreign key in this schema (Phase
  2.1–3.2) intentionally cascades: deleting a user removes their role
  assignments and org memberships, because those records only mean
  anything in the context of an existing user. An audit log is the
  opposite case — the entire point is that the historical record survives
  the thing it references being removed. This is directly tested (not
  just asserted from the model's docstring): deleting the actor or the
  organization leaves the row in place with the corresponding column
  nulled out.
- **`target_id` is deliberately not a foreign key.** What it points to
  varies by `target_type` ("user", "role", "permission", "organization",
  ...), and one column can't hold a real FK to more than one table. This
  is the standard, accepted trade-off for a polymorphic reference — no
  referential integrity is enforced on it at the database level, only by
  convention.
- **`action`/`target_type` are plain strings, not a fixed Postgres
  `ENUM`.** Same "plain data, no schema change needed to extend"
  philosophy the Phase 2.1 seed migration used for
  `Permission.resource`/`action` — a new phase introducing a new kind of
  auditable event never requires a migration, just a new string constant.
- **The JSONB column is named `event_metadata`, not `metadata`.**
  SQLAlchemy's declarative `Base` reserves `metadata` as the class
  attribute holding `Base.metadata` (the `MetaData` registry) — naming a
  mapped column `metadata` would collide with it. Caught before it became
  a runtime error, not after.
- **No update or delete method is planned for this table's repository
  (Phase 4.2), by design.** Same shape as `PermissionRepository`'s
  deliberate absence of a `create_permission` method — an audit log that
  can be edited or removed after the fact isn't an audit log.

## What This Phase Enables for Phase 4.2

A migrated, tested schema ready for `AuditLogRepository` (Phase 4.2) to
write to and query — no further schema changes anticipated for Phase 4.2,
4.3 (wiring `AuthService`/`AuthorizationService`/`OrganizationService` to
actually record events), or 4.4 (a query API).
